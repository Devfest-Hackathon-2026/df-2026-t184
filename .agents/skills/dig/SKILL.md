# Dig — 前提とリスクの1ラウンド洗い出し

計画・実装方針の暗黙の前提と未考慮リスクを表面化し、1ラウンドの構造化質問で本人の判断を取って記録する。ループしない（1ラウンド・1記録で終了）。

## 手順

### Phase 1. コンテキスト収集

質問を作る前に状況を把握する:

- 関連する計画・依頼・会話の文脈を確認する
- `AGENTS.md`、`docs/HACKATHON.md`、`docs/DECISIONS.md`、`docs/STATUS.md` など対象PJの規約・記録を読む
- 計画が参照する設計書・コードを読む

内部で整理する: 表明された目的 / 表明された制約 / 暗黙の前提 / 未着手の論点。ここではまだ質問しない。調べられる事実を本人に聞かず、情報取得の質問を押し付けない。

### Phase 2. 前提マッピング

暗黙の前提を次の6種のリスクに分類し、間違っていた場合の影響の大きい順に並べる:

- **実現可能性** — 「この技術で作れる」
- **ユーザー** — 「利用者はこう振る舞う」
- **スコープ** — 「この機能にはXが含まれる/含まれない」
- **依存** — 「サービス・API・担当者は使える/安定している」
- **スケジュール** — 「この期間でできる」
- **アーキテクチャ** — 「現在の構成がこれを支える」

影響の大きい前提が質問の種になる。

### Phase 3. 質問1ラウンド（2〜4問）

[共通の質問形式](../own-the-why/references/question-format.md) に従い、1ラウンドだけ 2〜4問を出す:

- 各質問に具体候補 2〜4個と pros/cons、AI推奨を添える
- 隠れた判断・トレードオフ・失敗モード・依存のフォールバック・ロールバック・運用負担を狙う
- UI の上限を超えるときは独立した問に分割する。数合わせの質問はしない
- 回答を待つ。無回答・事前選択を決定扱いしない

このラウンドのあと質問は繰り返さない。残った論点は記録に「未解決」として残す。

### Phase 4. 記録

回答を `docs/decisions/YYYY-MM-DD-<slug>.md`（型は `docs/decisions/README.md`）に書く:

- 質問文と候補
- 本人の選択を正確に引用
- 本人の理由（未回答は「未回答」のまま残し、推測で補完しない）
- AI 推奨、使った質問手段、結果

### Phase 5. 要約

短く報告して止める: 質問数、表面化した高リスク前提、決まった判断、未解決リスク、次の一手。別ラウンドを提案しない（単発が契約）。
