# retro: ループの振り返り

## 1. 数値を集める（数えられないものは「不明」と書く。推測で埋めない）
| 指標 | 出し方 |
| --- | --- |
| 周回数・所要時間 | `logs/run.log` の `[N]` と、最初と最後のコミットの時刻 |
| 評価回数と差し戻し率 | `logs/eval-*-F*.md` の数と、そのうち1行目が PASS でないものの割合 |
| 空回り | run.log に出た「変更なし」と「worker を停止」の回数 |
| 採点の推移 | `logs/scores.txt` |
| 費用 | `logs/costs.txt`（費用を出さない CLI は `?` になるので、トークン数を使う）と、各サービスの請求画面（人間に見てもらう） |

## 2. 判定の質を確かめる
- **偽 PASS**: PASS した機能を2〜3個選び、完了条件を自分で確かめる。人間に「動かない」と言われた機能は必ず入れる
- **偽 NEEDS_WORK**: 完了条件にない要求で差し戻した指摘を数える
- **NEEDS_WORK が0回だったとき**: わざと壊した機能を1つ評価させ、本当に差し戻すかを確かめるよう提案する

## 3. 分類して直し方を提案する
| 分類 | 直す場所 |
| --- | --- |
| 仕様（機能が大きい、完了条件があいまい、依存の漏れ、同じファイルを触る機能を並列にした） | `prompts/planner.md`、`docs/RULES.md` |
| 実装（同じミスを繰り返す、デグレ、ルール違反、出典のない数値） | `prompts/worker.md`、`AGENTS.md` |
| 判定（偽 PASS／偽 NEEDS_WORK） | `prompts/evaluator.md` |
| 環境（認証、デプロイ、CLI、スクリプト） | `bin/superloop`、`lib/agent.sh`、`docs/RUNBOOK.md` |

そのプロジェクトだけで直すなら、`.superloop/prompts/<役割>.md` に上書き版を置く。ハーネス本体を直すかどうかは人間が決める。一度だけ起きたことを全体の規則にしない。直す前に、再発しそうかどうかを書き添える。
