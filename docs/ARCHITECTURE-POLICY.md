# 寄り道MAP：合意した方針と残論点

2026-11-09、PMとの共有理解を確認済み。個別サービスの全採用、有料資源の作成、本番公開の承認ではない。

## 合意した方針

1. 誰でも楽しめる地図を共通の入口とし、言語・移動条件に応じた支援で楽しむ機会を広げる。
2. 東京の限定経路で公開3Dモデル・標高データから坂や時間帯別の日陰を計算し、現地未検証の推定値として表示する。現地検証は今回の範囲外。
3. 指定条件に必要なデータが欠ける候補や計算不能な候補は出さない。候補ゼロでも条件を自動で緩めず、段差・幅員等の通行可否を坂や日陰から保証しない。
4. 発表後は招待した少人数で「楽しさ＋選びやすさ」を検証する。情報は実証前後にチーム全員で確認する。
5. Firebase＋地理データの事前計算・配信を第一候補とする。広域の独自経路探索やSQLは必要性を見て判断し、追加支出は個別に提案・承認を得る。

坂・日陰で「確認できた」とするのは、推定に必要なデータと計算結果を確認できること。現実の道路での条件適合が実証済みという意味ではない。推定値では判定できない通行条件を適合扱いにしない。

## 決めた理由

### 本人が明示した理由

共通体験は、観光客や障害のある人も同じように楽しめるようにするため。
推定値の利用は、現地検証まではできない制約と、公開モデルで坂・日陰を扱えることをサービス化の根拠にしたいという意図による。

選択肢を選んだ項目は、その選択肢の理由を本人が採用した（2026-11-09 本人確認）。

- 少人数の限定実証：学びを得ながら範囲を管理できる。
- 東京の限定経路で実データを試す：範囲は狭いが、体験とデータ品質を検証できる。
- 追加支出は個別承認：費用を確認して進められる。
- 実証前後にチーム全員で確認：負担を分担できる（確認漏れを防ぐ手順が必要）。
- 条件を確認できた候補だけ表示：判断しやすい（候補ゼロもあり得る）。
- 楽しさ＋選びやすさで評価：行きたい寄り道が見つかり、支援情報と不明点を理解して自分に合う候補を選べるかを確かめる。

インクルーシブ機能を加える理由には、本人の「対応した方が個人的には発表もしやすい」という発言もある。AIの推奨理由は本人の理由と分けて下に記す。

### AIが提示した設計上の理由

Firebaseを第一候補にするのは、既存のNext.js実装と環境設定を活用するため。最適な費用・性能が実測で証明されたわけではない。
事前計算は、建物・標高の重い処理を画面表示のたびに繰り返さないため。処理時間・配信量・更新間隔は未検証。
SQLと独自広域探索の先送りは、限定経路の比較だけでは必要性が確定していないため。対象範囲や検索要件が変われば再評価する。

公開データと手法の存在は技術的な見通しの根拠になる。一方、当アプリでの計算成功、現地精度、利用者への効果は別の証拠が必要。[国土地理院の標高仕様](https://service.gsi.go.jp/kiban/app/help/)と[国交省の日時別日陰シミュレーション解説](https://www.mlit.go.jp/plateau/learning/tpc02-2/)を参照。

## 後続の残論点

1. **データと地区**：区域別のデータ、年度・詳細度・欠損率・利用条件を調査して地区と経路を選ぶ。オープンデータと計算ソフトのOSSライセンスは別に確認する。
2. **支援の具体範囲**：対応言語・移動条件・表示項目・災害案内の初回範囲を決める。全言語・全障害・災害時の安全経路対応が合意済みとは扱わない。
3. **計算品質**：モデル上の検算、既知形状での確認、橋・地下・樹木・庇の扱い、鮮度・更新基準を定める。計算検証は現地精度の証明とは分ける。
4. **実証手順**：参加者、評価方法、成功の具体的基準、出典・データ版・計算条件・欠損・表示を全員で確認するチェックリストを決める。
5. **実装と費用**：公式日程の照合、作業量と利用量別の試算を行い、サービスの個別採否・設定値を提案する。追加支出の承認前に該当資源を構築しない。
