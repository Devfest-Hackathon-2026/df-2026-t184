### 目的・スコープ

`/terrain` の数値を、デモとこれから作るモックで使える値にする。やることは2つ。
（1）推定最大勾配が跳ねる不具合を直す。（2）日陰グリッドをデモ日の毎正時にする。

### 観測した事実（コード・データから）

- `samplePolyline` は 10m 間隔で打ち直した後、10m 未満の端数区間を末尾に足す（1m 未満のこともある）。
  `slopeMetrics` は区間ごとに |標高差| / 距離 を取っていたので、末尾の端数で勾配が跳ねていた。
  修正前に跳ねた値（直線の最短ルート・OSM 徒歩経路の再現）は（未記入: 要調査）
  （2026-11-10 F08 で追記: 元の記録にあった値は、再現手順と出典が残っていないため削除した）
- 2026-11-14 の東京は 17:00 JST で太陽高度が 0 以下（`src/lib/terrain/sun.ts` の NOAA 近似式で算出。
  式の出典: [NOAA Solar Calculations](https://gml.noaa.gov/grad/solcalc/solareqns.PDF)）。
  16:00 は 5.8°、07:00 は 7.5°（同じ `solarPosition` を北緯 35.721・東経 139.771 で 2026-11-10 に再計算して一致を確認）
- 日陰グリッドの旧形式は Uint8 で bit7 を評価不能に使うため、時刻は 7 個までしか入らない

### 実施判断（委譲範囲・本人の回答ではない）

- 勾配: `slopeMetrics` に `gradientBaselineM` を追加した（`/terrain` では 10m）。欠損で切れない連続区間ごとに、
  区間を基準長以上になるまで束ねて勾配を取る。末尾の端数は直前の区間に併合する。
  基準長の窓が一つも取れないときの最大勾配は null（不明）。累積上昇・下降と評価済み区間率の意味は変えない。
  数値だけを頭打ちにするガードは採らなかった。原因は区間長の不足で、頭打ちは値の意味を壊すため
  - 結果: 修正後の推定最大勾配は直線の最短ルート 31.0%、寄り道ルート 21.0%
    （2026-11-10 F08 で、地図キーなし＝直線評価の `/terrain` 画面に表示される値として再確認。修正前の値と、
    端数を捨てた場合の値は（未記入: 要調査））。段差の上昇を捨てずに 10.3m で評価する
- 日陰グリッドの形式: セル値を Uint16（bit0..14 = 時刻、bit15 = 評価不能、形式名 `yorimichi-shade-v2`）にした。
  旧形式の読み込みは残していない（生成物はリポジトリ内の 1 ファイルで、同時に差し替えた）。
  候補として「時刻ごとのビット平面」も考えたが、参照コードが複雑になる割にサイズ差が小さい見込みだったので採らなかった（サイズ差の実測値は（未記入: 要調査））
- スクリプト: `--date` と `--hours` を必須引数にした。既定値をコードに残すと、設定がまた定数に戻るため。
  夜間時刻が含まれると従来どおりエラーで止める
- 日付・時刻: 2026-11-14 の 07:00〜16:00 の毎正時（10 時刻）。日付は Regional Day に合わせた
  （`docs/HACKATHON.md`。二次資料の転記で公式原本とは未照合）。
  **ブリーフの決定は 07:00〜17:00 だったが、17:00 は日没後のため含めていない**
- UI: 推定日陰率を 1 行にし、行見出しの `<select>` で時刻を選ぶ。既定は現在時刻（JST）に最も近い時刻で、
  範囲外なら近い方の端。注意点の日陰の文言はグリッドの `times` から出す
